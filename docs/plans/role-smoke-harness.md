## Проблема

Сейчас агент не может выполнить ни один авторизованный UI-сценарий: вход в приложение — только Google OAuth (`src/pages/Login.tsx` → `signInWithGoogle`), сессия живёт в IndexedDB, Playwright `storageState` её не переносит. Из-за этого смоук админки, прав по курсам и студенческих сценариев остаётся ручной работой Алексея. Последний пример — приёмка кабинета автора (`docs/plans/author-cabinet.md`): код и rules покрыты тестами, но «посмотреть глазами под ролью админа курса» пришлось откладывать.

## Цель

Локальный стенд, на котором агент запускает приложение против Firebase-эмуляторов, входит **под любой ролью без Google OAuth**, и прогоняет сценарии — в том числе несколькими субагентами параллельно, каждый в своей изолированной песочнице данных.

Ключевое требование безопасности: **ничего из этого не должно существовать в проде**. Никаких service-account ключей, никакого нового способа входа в прод-сборке, никаких обращений к прод-Firestore.

## Карта текущего состояния (проверено 2026-08-29)

**Уже есть:**

- `src/lib/firebase.ts:56-62` — режим эмуляторов за флагом сборки `VITE_USE_FIREBASE_EMULATORS === "true"`: `connectAuthEmulator(9099)`, `connectFirestoreEmulator(8080)`, `connectStorageEmulator(9199)`. Флаг вшивается на этапе сборки, в Vercel его нет.
- `tests/integration/firebase.test.json` — конфиг эмуляторов (project `psych-dev-site-test`, firestore 8080 / auth 9099 / storage 9199), rules берутся из **прод-файла** `firestore.rules`.
- `package.json`: `firebase:emulators:start`, `test:integration`, `test:e2e`, `test:e2e:prod`; `firebase-admin@^13` в зависимостях корня.
- `playwright.config.ts` — один проект `chromium`, `baseURL: http://localhost:4175`, `webServer: npm run preview -- --port 4175`, `fullyParallel: true`.
- `tests/e2e/production-smoke.spec.ts` — единственный e2e-файл, гостевые сценарии.

**Чего нет:** сид-скриптов для эмулятора, способа войти без Google, ролевых Playwright-проектов, изоляции параллельных прогонов.

**Как устроены роли (это и надо уметь воспроизводить):**

| Роль | Что должно быть в эмуляторе |
|---|---|
| Гость | без авторизации |
| Студент без доступа | Auth-пользователь + `users/{uid}` без `courseAccess` |
| Студент курса | `users/{uid}.courseAccess: { development: true }` |
| Студент группы | `groups/{gid}.memberIds` содержит uid, `grantedCourses: ['clinical']` (union считается в `useAuthStore`) |
| Админ курса | claim `role: 'admin'` + claim `editableCourses: ['external-x']` + зеркало `users/{uid}.adminEditableCourses` |
| Админ без курсов | claim `role: 'admin'`, `editableCourses: []` |
| Co-admin | claim `coAdmin: true` + `users/{uid}.coAdmin: true` |
| Super-admin | email `biboandbobo2@gmail.com` (`src/constants/superAdmin.ts` — распознаётся по email) |

Клиент читает роль из custom claims токена (`src/stores/useAuthStore.ts`), права на курсы — пересечение claim `editableCourses` и зеркала `users/{uid}.adminEditableCourses`. Rules (`firestore.rules`) читают только claim. Значит **сид обязан выставлять и claim, и Firestore-документ** — иначе роль будет вести себя не так, как в проде.

## Объём работ

### Этап 1 — вход под ролью без OAuth

1. **Dev-only точка входа.** Под тем же флагом `VITE_USE_FIREBASE_EMULATORS === 'true'` (и только под ним) дать тестам способ авторизоваться: например, `window.__testAuth = { signInWithCustomToken, signInWithEmailAndPassword, signOut }` в `src/lib/firebase.ts` или в отдельном dev-модуле, который импортируется динамически только при включённом флаге. Требования:
   - в прод-бандле кода быть не должно — проверь `npm run build` и `grep` по `dist/` (обязательный пункт приёмки);
   - прод-вход (`signInWithGoogle`) не трогать;
   - `console.*` запрещён, только `debugLog`.
2. **Проверить альтернативу перед реализацией:** Auth-эмулятор умеет отдавать Google-popup заглушку («Add new account»), и Playwright может её прокликать. Если это окажется надёжнее и меньше по коду — выбери этот путь и обоснуй в отчёте; тогда п.1 не нужен. Решение принимай сам, но зафиксируй выбор и причину.

### Этап 2 — сид ролей

3. **Скрипт `scripts/seedEmulatorRoles.ts`** (tsx, стиль — как соседние скрипты в `scripts/`): через `firebase-admin`, подключённый к эмуляторам (`FIREBASE_AUTH_EMULATOR_HOST=127.0.0.1:9099`, `FIRESTORE_EMULATOR_HOST=127.0.0.1:8080` — ключи не нужны), создаёт:
   - пользователей всех ролей из таблицы выше, с custom claims и зеркалами в `users/{uid}`;
   - минимальный контент: core-курсы `development`/`clinical`, динамический курс `external-x` (опубликованный) и `external-hidden` (скрытый), по 2–3 занятия в каждом, группу с `grantedCourses`, пару `lectureQuestions` и несколько `feature_events` с разными `courseId` (нужны для проверки сводки телеметрии);
   - параметр `--project <id>` для изоляции параллельных прогонов и `--reset` для чистки.
   Скрипт должен быть идемпотентным.
4. **Фикстуры для Playwright**: описание ролей (email, uid, ожидаемые права) в одном месте, чтобы тесты и сид не расходились.

### Этап 3 — параллельность и изоляция

5. **Изоляция песочниц.** Firestore-эмулятор держит несколько `projectId` одновременно — используй это: каждый параллельный прогон работает в своём проекте (`smoke-a`, `smoke-b`, …). Проблема: `projectId` приходит в клиент из env на этапе сборки. Реши одним из способов (выбери сам, обоснуй):
   - **(рекомендуется)** dev-only переопределение `projectId` из query-параметра (`?testProject=smoke-a`) в `src/lib/firebase.ts` под флагом эмуляторов — один dev-сервер обслуживает все прогоны;
   - либо N dev-серверов на разных портах с разными `VITE_FIREBASE_PROJECT_ID`.
6. **Playwright-проекты по ролям** в `playwright.config.ts` (`smoke:student`, `smoke:author`, `smoke:superadmin`, …) со своими `storageState`/setup-проектом, чтобы вход выполнялся один раз на роль.
7. **Точка запуска для агента**: один npm-скрипт, который поднимает эмулятор, сидит данные, поднимает dev/preview и прогоняет выбранные роли — например `npm run smoke:roles -- --roles author,superadmin`. Он должен корректно гасить процессы при выходе (у существующего `test:e2e:prod` с этим проблемы — preview остаётся висеть, проверь и не повтори).

### Этап 4 — сценарии кабинета автора (первая полезная нагрузка)

8. Написать в `tests/e2e/` ролевые сценарии, закрывающие критерии приёмки `docs/plans/author-cabinet.md`:
   - админ курса `external-x`: `/admin` показывает кабинет автора со своим курсом; в сайдбаре и `/admin/content` только `external-x`; чужой курс недоступен по прямой ссылке `/admin/content/edit/<id>?course=development`; кнопки «Добавить курс» нет; «Создать тест» доступна; `/admin/telemetry` показывает только его события;
   - админ без курсов: заглушки вместо пустых экранов, запросов к телеметрии не уходит;
   - super-admin: все курсы, все кнопки, `/superadmin/telemetry` с блоком «Посещения страниц», `/admin` по-прежнему редиректит на `/superadmin`;
   - студент группы: видит только открытые ему курсы, в админку не попадает.
9. Прогнать эти сценарии субагентами параллельно (по роли на субагента, каждый в своей песочнице) и убедиться, что прогоны не мешают друг другу.

## Критерии приёмки

1. `npm run smoke:roles` (или как назовёшь) поднимает стенд с нуля одной командой и завершается, не оставляя висящих процессов (`pgrep -f "vite|firebase emulators"` пуст после выхода).
2. Агент входит под каждой ролью из таблицы без Google OAuth и без единого сетевого запроса к прод-Firebase.
3. Два и более параллельных прогонов не портят данные друг другу.
4. Сценарии этапа 4 проходят и реально ловят регрессию: временно сломай один гейт (например, верни `useCourses` вместо `useEditableCourses` в сайдбаре) — соответствующий тест должен упасть. Верни как было.
5. `npm run build` не содержит dev-only кода входа: `grep -r "__testAuth\|testProject" dist/` пуст.
6. `npm run validate` зелёный; `npm run test:integration` 107/107 не сломаны.
7. Прод-вход через Google по-прежнему работает (проверить в обычном `npm run dev` без флага эмуляторов — кнопка на месте, редиректы прежние).

## Ограничения процесса

- Ветка отдельная (`feat/role-smoke-harness`), **`main` не трогать**, merge — только с одобрения Алексея.
- Никаких service-account ключей в репозитории и в env-файлах. Эмулятору credentials не нужны.
- Никаких обращений к прод-проекту `psych-dev-site-prod` из стенда — ни чтения, ни записи.
- `console.*` запрещён (`debugLog`/`debugError` из `@/lib/debug`); новые файлы < 500 строк; barrel exports по проектному стандарту.
- Не добавлять файлы в `api/` (лимит Vercel-функций).
- Коммиты по шагам; push — после финального коммита этапа.
